## 단위 테스트 범위

### 1. 단위 테스트 작성의 이점

- 단위 테스트는 모든 사람이 코드의 세부 사항을 파악하고 작동 방식을 이해하는 데 도움이 됩니다.
- 테스트 케이스를 통해 버그를 찾고 강력한 코드를 제출할 수 있습니다.
- 테스트 케이스는 코드의 데모 사용이기도 합니다.

### 2. 단위 테스트 케이스의 일부 디자인 원칙

- 단계, 세분화 및 조건 조합을 신중하게 설계해야 합니다.
- 경계조건에 주의하세요.
- 단위 테스트는 잘 설계되어야 하며 쓸모없는 코드는 피해야 합니다.
- 단위 테스트 작성이 어려운 '메서드'를 발견하고, 해당 '메서드'가 '잘못된 코드'임을 확인한 경우 개발자와 함께 리팩터링합니다.

- DolphinScheduler: [mockito](http://site.mockito.org/).다음은 몇 가지 개발 가이드입니다: [mockito 튜토리얼](http://www.baeldung.com/bdd-mockito), [mockito refcard](https://dzone.com/refcardz/mockito)

<!-- markdown-link-check-enable -->
- TDD(옵션): 새로운 기능을 작성하기 시작하면 먼저 테스트 케이스 작성을 시도해 볼 수 있습니다.

### 3. 테스트 커버리지 설정값

- 이 단계에서 델타 변경 코드의 테스트 적용 범위에 대한 기본값은 >= 60%이며 높을수록 좋습니다.
- 이 페이지에서 테스트 보고서를 볼 수 있습니다: https://codecov.io/gh/apache/dolphinscheduler

## 단위 테스트를 위한 기본 지침

### 1. 고립과 단일성

테스트 케이스는 메소드 수준까지 정확해야 하며, 테스트 케이스만 단독으로 실행할 수 있어야 합니다.동시에 초점은 항상 방법에 있습니다(방법만 테스트됩니다).

방법이 너무 복잡하면 개발 단계에서 다시 분할해야 합니다.테스트 케이스의 경우 케이스가 하나의 분기(판단)에만 초점을 맞추는 것이 가장 좋습니다.변경 사항이 적용되면 테스트 사례의 성공에만 영향을 미칩니다.이를 통해 개발 단계에서 문제 확인 및 문제 해결이 크게 촉진될 것입니다.그러나 동시에 적용 범위 측면에서 큰 어려움을 안겨주기도 합니다.

### 2. 자동성

단위 테스트를 자동화할 수 있습니다.필수: 모든 단위 테스트는 src/test 아래에 작성되어야 합니다.또한 메소드 이름 지정은 사양을 준수해야 합니다.벤치마크 테스트는 제외됩니다.

### 3. 재현성

여러 번 실행하면(어떤 환경에서든 언제든지) 고유하고 반복 가능한 결과가 생성됩니다.

### 4. 경량

즉, 어떠한 환경이라도 신속하게 구현할 수 있습니다.

이를 위해서는 다양한 스프링 콩 등과 같은 너무 많은 구성 요소에 의존하지 않아야 합니다.이것들은 모두 단위 테스트의 모의 테스트이며, 이를 추가하면 단일 테스트 실행 속도가 빨라지고 잠재적으로 오염이 전달될 수 있습니다.

일부 데이터베이스, 기타 외부 구성 요소 등의 경우 가능한 한 모의 클라이언트는 외부 환경에 의존하지 않습니다(외부 종속성이 있으면 테스트 사례의 이식성과 안정성 및 결과의 정확성이 크게 제한됨). 이는 또한 개발자가 어떤 환경에서든 쉽게 테스트할 수 있도록 해줍니다.

### 5. 측정 가능

수년에 걸쳐 mockito는 NO.1 모의 제품으로 성장했지만 여전히 모의 정적 메서드, 생성자 등을 지원하지 않습니다. 심지어 웹사이트에서도 "모든 것을 모의하지 마세요"라고 계속 말하고 있습니다.따라서 정적 메소드를 가능한 한 적게 사용하십시오.

일반적으로 일부 유틸리티 클래스에서만 정적 메서드를 제공하는 것이 좋습니다. 이 경우 모의 객체가 필요하지 않고 실제 클래스만 사용합니다.종속 클래스가 유틸리티 클래스가 아닌 경우 정적 메서드를 인스턴스 메서드로 리팩터링할 수 있습니다.이는 객체 지향 설계 개념에 더 부합합니다.

### 6. 완전성

테스트 커버리지, 이것은 매우 어려운 문제입니다.핵심 프로세스의 경우 90% 적용 범위를 달성하고 비핵심 프로세스 요구 사항은 60% 이상 달성하기를 희망합니다.

적용 범위가 충분히 높으면 버그 발생 가능성이 줄어들고 회귀 테스트 비용도 절감됩니다.이는 긴 프로세스이므로 개발자가 코드를 추가하거나 수정할 때마다 테스트 사례를 동시에 개선해야 합니다.개발자와 관련 코드 검토자는 이 점에 대해 충분한 관심을 가져주시길 바랍니다.### 7. 무효 주장 거부

잘못된 주장은 테스트 자체를 의미 없게 만들고, 코드가 올바른지 여부와는 거의 관련이 없습니다.그리고 코드가 프로덕션에 배포될 때까지 지속될 수 있는 성공에 대한 환상을 만들 위험이 있습니다.

잘못된 어설션에는 여러 가지 유형이 있습니다.

1. 다양한 유형의 비교.

2. 기본값이 있는 개체나 변수가 null이 아닌지 확인합니다.

이것은 의미가 없는 것 같습니다.따라서 관련 판단을 내릴 때 기본값 자체가 포함되어 있는지 여부에 주의해야 합니다.

3. 주장은 가능하다면 부정보다는 긍정이어야 합니다.코드가 비어 있는지 여부만 고려하지 않는 한, 어설션은 가능할 때마다 예측된 결과 또는 정확한 값의 범위 내에 있어야 합니다(그렇지 않으면 실제 기대와 일치하지 않지만 어설션을 통과하는 결과가 나올 수 있음).

### 8. 단위 테스트 시 주의할 점

1: 스레드.수면()

테스트 코드에서 Thread.sleep을 사용하지 마십시오. 테스트가 불안정해지고 환경이나 로드로 인해 예기치 않게 실패할 수 있습니다.다음 접근 방식이 권장됩니다.

`Awaitility.await().atMost(...)`

2: 일부 테스트 클래스를 무시합니다.

@Disabled 주석은 후속 개발자가 테스트가 무시된 이유에 대한 기록을 추적할 수 있도록 관련 문제 주소에 연결되어야 합니다.

예를 들어 @Disabled("#1 참조")입니다.

3: try-catch 단위 테스트 예외

단위 테스트의 코드에서 예외가 발생하면 테스트가 실패합니다.따라서 예외를 포착하기 위해 try-catch를 사용할 필요가 없습니다.        ```java
        @Test
        public void testMethod() {
          try {
                    // Some code
          } catch (MyException e) {
            Assert.fail(e.getMessage());  // Noncompliant
          }
        }
````

다음을 수행해야 합니다.```java
@Test
public void testMethod() throws MyException {
    // Some code
}
````

4: 테스트 예외

예외를 테스트해야 하는 경우 테스트 코드에 여러 메서드 호출을 포함하지 않아야 하며(특히 동일한 예외를 발생시킬 수 있는 메서드가 여러 개 있는 경우) 테스트 대상을 명확하게 명시해야 합니다.

5: MockitoJUnitRunner.Silent.class 사용을 거부합니다.

단위 테스트에서 UnnecessaryStubbingException이 발생하면 이를 해결하기 위해 먼저 @RunWith(MockitoJUnitRunner.Silent.class)를 사용하는 것을 고려하지 마세요.이는 문제를 숨길 뿐이며, 예외 힌트를 따라 문제의 문제를 해결해야 하는데, 이는 어려운 작업이 아닙니다.변경이 완료되면 코드가 다시 훨씬 깔끔해졌음을 알 수 있습니다.
