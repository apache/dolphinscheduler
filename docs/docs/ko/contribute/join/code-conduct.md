# 행동강령

다음 행동 강령은 [Apache Software Foundation 행동 강령](https://www.apache.org/foundation/policies/conduct.html)의 완전한 준수를 기반으로 합니다.

## 개발 철학

- **일관적** 코드 스타일, 이름 지정 및 사용법이 일관됩니다.
- **읽기 쉬움** 코드는 명확하고, 읽고 이해하기 쉬우며, 디버깅할 때 코드의 의도를 알 수 있습니다.
- **Neat**은 《리팩토링》과 《코드 청결성》의 개념에 동의하며 깨끗하고 우아한 코드를 추구합니다.
- **추상** 계층 구조가 명확하고 개념이 세련되고 합리적입니다.메서드, 클래스, 패키지 및 모듈을 동일한 추상화 수준으로 유지합니다.
- **마음** 책임감을 갖고 장인의 정신으로 계속 조각해 나갑니다.

## 개발 사양

- `mvn -U clean package -Prelease`를 실행하면 모든 테스트 케이스를 통해 컴파일하고 테스트할 수 있습니다.
- 테스트 적용 범위 도구는 개발 분기 적용 범위 이상을 확인합니다.
- 루트 디렉터리에서 Checkstyle을 사용하여 코드에서 유효성 검사 규칙을 위반한 특별한 이유가 있는지 확인하세요.템플릿 위치는 ds_check_style.xml에 있습니다.
- 코딩 사양을 따르세요.

## 코딩 사양

- 리눅스 줄바꿈을 사용하세요.
- 들여쓰기(빈 줄 포함)는 마지막 줄과 일치합니다.
- 클래스 선언과 다음 변수 또는 메소드 사이에는 빈 줄이 필요합니다.
- 의미 없는 빈 줄이 없어야 합니다.
- 클래스, 메소드, 변수는 이름에서 알 수 있듯이 이름을 지정해야 하며 약어는 피해야 합니다.
- 반환 값 변수는 `result`를 따서 명명됩니다.`each`는 루프에서 루프 변수의 이름을 지정하는 데 사용됩니다.그리고 map에서는 `each` 대신 `entry`가 사용됩니다.
- 캐시된 예외는 'e'라고 합니다.예외를 포착하고 아무것도 하지 않으며 예외 이름은 '무시됨'으로 지정됩니다.
- 구성 파일 이름은 camelCase로 지정되며, 파일 이름은 이니셜/시작 문자가 대문자인 소문자입니다.
- 주석 해석이 필요한 코드는 가능한 한 작게 작성하고 메소드 이름으로 해석해야 합니다.
- `같음` 및 `==` 조건식에서는 상수가 왼쪽, 변수는 오른쪽에, 조건보다 큼 조건식에서는 변수가 왼쪽, 상수가 오른쪽에 옵니다.
- 상속에 사용되는 추상 클래스 외에 클래스를 '최종'으로 설계해 보세요.
- 중첩 루프는 가능한 한 많은 방법입니다.
- 멤버 변수가 정의되는 순서와 매개변수가 전달되는 순서는 클래스와 메소드 전체에서 일관됩니다.
- 가드문 사용을 우선으로 합니다.
- 클래스와 메소드에는 최소한의 액세스 제어가 있습니다.
- 메소드가 사용하는 프라이빗 메소드는 메소드를 따라야 하며, 프라이빗 메소드가 여러 개인 경우 작성하는 프라이빗 메소드는 원래 메소드의 프라이빗 메소드와 동일한 순서로 나타나야 합니다.
- 메소드 입력 및 반환 값은 'null'이 될 수 없습니다.
- if else의 반환 및 할당 문은 삼중 목적 연산자와 함께 선호됩니다.
- 'LinkedList'에 우선순위가 부여되며 인덱스를 통해 컬렉션의 요소 값을 가져와야 하는 경우에만 'ArrayList'를 사용합니다.
- 확장을 생성할 수 있는 `ArrayList`, `HashMap`과 같은 컬렉션 유형은 확장을 방지하기 위해 컬렉션의 초기 크기를 지정해야 합니다.
- 로그와 메모는 항상 영어로 작성됩니다.
- 주석에는 `javadoc`, `todo` 및 `fixme`만 포함될 수 있습니다.
- 노출된 클래스와 메서드에는 javadoc이 있어야 하며, 상위 클래스를 재정의하는 다른 클래스와 메서드 및 메서드에는 javadoc이 필요하지 않습니다.

## 단위 테스트 사양- 테스트 코드와 생산 코드는 동일한 코드 사양을 따릅니다.
- 단위 테스트에는 AIR(Automatic, Independent, Repeatable) 설계 개념이 적용됩니다.
- 자동: 단위 테스트는 대화형이 아닌 완전히 자동화되어야 합니다.출력 결과를 수동으로 확인하는 것은 금지되어 있으며 `System.out`, `log` 등은 허용되지 않으며 어설션을 통해 확인해야 합니다.
- 독립적: 단위 테스트 케이스 간에 서로 호출하고 실행 순서에 의존하는 것이 금지됩니다.각 단위 테스트는 독립적으로 실행될 수 있습니다.
- 반복 가능(Repeatable): 단위 테스트는 외부 환경의 영향을 받지 않고 반복 가능합니다.
- 단위 테스트에는 BCDE(Border, Correct, Design, Error) 설계 원칙이 적용됩니다.
- 경계(경계 값 테스트) : 루프 경계의 경계, 특수 값, 데이터 순서 등을 입력하여 예상되는 결과를 얻습니다.
- Correct(정확성 테스트): 올바른 입력으로 예상한 결과를 얻습니다.
- 디자인(합리성 디자인): 프로덕션 코드 디자인과 결합하여 고품질의 단위 테스트를 디자인합니다.
- 오류(내결함성 테스트): 불법적인 데이터, 비정상적인 흐름 등 잘못된 입력을 통해 예상한 결과를 얻습니다.
- 특별한 사유가 없는 경우에는 검사를 전액 보장해야 합니다.
- 각 테스트 케이스는 정확하게 어설션되어야 합니다.
- 테스트 코드와 코드 분리를 위한 환경을 준비한다.
- jUnit `Assert`, hamcrest `CoreMatchers`, Mockito Correlation만 정적 가져오기를 사용할 수 있습니다.
- 단일 데이터 어설션은 `assertTrue`, `assertFalse`, `assertNull` 및 `assertNotNull`을 사용해야 합니다.
- 다중 데이터 어설션은 `assertThat`을 사용해야 합니다.
- 정확한 주장입니다. 'not', 'containsString' 주장을 사용하지 마세요.
- 테스트 케이스의 참값은 ActualXXX로, 기대값은 ExpectXXX로 명명해야 합니다.
- `@Test` 라벨이 있는 클래스 및 메소드에는 javadoc이 필요하지 않습니다.
- 공개 사양.
- 각 줄의 길이는 '200' 이하여야 하며 각 줄은 이해하기 쉽도록 의미적으로 완전해야 합니다.
